## 2026-11-25 binder 调用量实测

### 测量方法

```bash
# 读累计计数器，采样两次算速率
adb shell cat /dev/binderfs/binder_logs/stats | grep -E '^BC_TRANSACTION|^BC_TRANSACTION_SG'
```

`BC_TRANSACTION + BC_TRANSACTION_SG` = 客户端发起的 binder 调用总数。

> `/proc/binder/stats` 在这台车机上不存在；binderfs 在 `/dev/binderfs/`（注意不是 `/sys/kernel/debug`）。

### 实测数据（12 秒窗口）

| 场景 | 12 秒增量 | **次/秒** |
|---|---|---|
| HUD 运行中（170 key + 双屏 WebView） | 20,053 | **1,671** |
| `force-stop ov.dash` 后 | 13,805 | **1,150** |
| **差值 = HUD 的开销** | 6,248 | **521** |

### 结论

1. **全系统 baseline 约 1,150 次/秒**，不是"几千次"量级
2. HUD 占 **31%**（521 / 1,671）
3. 但 521 的构成是：

   | 来源 | 次/秒 | 占比 |
   |---|---|---|
   | 170 个车辆 key 的 `transact(4)` | 170 | 33% |
   | **WebView 渲染 + IPC** | ~350 | **67%** |

4. **大头是 WebView 不是 binder**。60fps 渲染每帧提交 SurfaceFlinger，加上 WebView renderer 进程 IPC

### 优化优先级（按收益排序）

| 措施 | 可省 | 怎么做 |
|---|---|---|
| 减少页面重绘 | **最多 350 次/秒** | 去掉 CSS 动画、减少 `position:fixed` 元素、避免每帧改 DOM |
| 精简 `keys.txt` 到 15 个 | 155 次/秒 | 删掉不用的行 |
| `refresh` 1000 → 2000 | ~85 次/秒 + 部分重绘 | 改 config |

## 2026-11-25 服务端 APK 才是 key 的权威来源

### 背景

`com.yg.clusterwall`（仪表屏Plus）是玩家自己做的 DIY app，**它的 key 也是逆向/试错来的，不能当权威**。

### 权威来源

```
/vendor/app/ZoneVehicleServer/ZoneVehicleServer.apk   15.7 MB，2 个 dex
/vendor/app/StatusDataService/StatusDataService.apk   2.7 MB，1 个 dex
```

服务端必须能解析每个 key 才能返回值，所以**完整 key 表一定在它里面**。

验证：现有 100 个 key 里 **98 个能在 `ZoneVehicleServer` 里找到**。

### 提取流程

```bash
adb pull /vendor/app/ZoneVehicleServer/ZoneVehicleServer.apk
unzip -o -q ZoneVehicleServer.apk "classes*.dex" -d /tmp/vs
strings /tmp/vs/*.dex | grep -E "^[A-Z][A-Z0-9_]{4,}$" | sort -u
```

- 9131 个大写常量 → 筛出 **375 个**带车辆前缀的（`BMS_ IPK_ SEAT_ HUD_ DOOR_ LIGHT_ MIRROR_ ADS_ VEH_ AC_ ODO_ POWER_ CHARGE_ ...`）
- **key 不能靠猜，要运行时试读**：对每个候选遍历 13 个子服务调 `transact(4)`，返回非 null 才算数
- 380 个候选 → **命中 170 个**

### 结果

| 服务 | 原 | 现 |
|---|---|---|

## 2026-11-25 launcher 总菜单是 ty=2630 私有窗口

### 现象

主屏 overlay 在桌面正常显示，但打开 launcher 的「总菜单」（应用抽屉）后 overlay 看不见了，而窗口本身还在（`dumpsys` 能查到）。

### 原因

`dumpsys window windows` 按 `mBaseLayer` 排序：

| Window | 名称 | package | mBaseLayer |
|---|---|---|---|
| #16 | **总菜单** | com.zone.hmi.launcher | **251000** |
| #18 | ov.dash | ov.dash | **221000** |
| #20 | MainWallpaperActivity（桌面） | com.zone.hmi.launcher | 21000 |

总菜单窗口属性：

```
ty=2630 fmt=TRANSLUCENT
fl=NOT_FOCUSABLE NOT_TOUCH_MODAL LAYOUT_NO_LIMITS WATCH_OUTSIDE_TOUCH
```

**`ty=2630` 是车厂私有的系统窗口类型**（AOSP 标准最高只到 `TYPE_APPLICATION_OVERLAY = 2038`）。第三方 app 拿不到这个类型，所以**永远盖不住它**。

### 更麻烦：检测不到

- `UsageEvents` 只能拿包名，而桌面和总菜单**都是 `com.zone.hmi.launcher` 的同一个 `MainWallpaperActivity`**
- 窗口列表只有 shell 能读，app 侧没有任何公开 API

**结论：总菜单下 overlay 会被完全遮住且无法感知。但视觉影响为零（用户看不见），只是 WebView 在空转。**

## 2026-11-25 onlyOnDesktop 的实现与坑

### 实现

```json
{ "display": 0, "onlyOnDesktop": true, "launcherPkg": "com.zone.hmi.launcher" }
```

- 每 `topCheckMs` 查一次 `UsageStatsManager.queryEvents()`
- 前台包名 != `launcherPkg` → `removeViewImmediate` + `web.destroy()`，`web` 置 null
- 回到桌面 → 重新 `new WebView` + `addView`，`lastJson` 清空保证首帧必推

### 三个必须满足的前提

1. **manifest 里声明 `PACKAGE_USAGE_STATS`** —— 只做 `appops set` 不生效，`queryEvents` 返回 0 个事件
2. **`adb shell appops set ov.dash GET_USAGE_STATS allow`**
3. **查询窗口要够大** —— `queryEvents` 只返回「切换事件」，用户不动就没有新事件。首次查 1 小时，之后查增量

### 不可靠的替代

`queryUsageStats()` 的 `getLastTimeUsed()` **不能用**：导航 app 在前台时它报的是 114 秒前的 launcher。只能用 `queryEvents`。

### 局限

- **launcher 内部页面切换无法区分**（桌面 ↔ 总菜单，同包名同 Activity）
- **无障碍服务可以做到实时**（`TYPE_WINDOW_STATE_CHANGED`），但车机设置里不一定有入口

## 2026-11-25 screencap 抓不到 QNX 层

**`adb shell screencap` 只抓 SurfaceFlinger 的 Android 合成结果，QNX 的物理 plane 完全不在截图里。**

后果：**副屏截图不等于屏幕实际显示**。QNX 的上下边栏、右侧导航信息栏在截图里是透明的，看起来像「什么都没盖」。

**已经因为这个判断错过一次**：看截图以为四张卡片完整可见，实际屏幕上右侧两张被 QNX 导航信息栏盖住，数值完全读不出来（用户反馈才发现）。

**规则：涉及副屏视觉的判断，必须让人看实车屏幕确认，不能只看截图。**

## 方法论：怎么排查「overlay 被遮挡」

1. `dumpsys window windows` 按 `mBaseLayer` 排序，看谁的 layer 高
2. **app 侧看不到目标窗口，但屏幕上确实被挡 → 大概率是 QNX 物理 plane**
3. 判据：**`screencap` 里有 = Android 层；`screencap` 里没有但屏幕上有 = QNX 层**
4. 用自己窗口做「探针」：在目标区域放一块不透明色块，让人看实车屏幕，被盖住就说明那层在上面

## 方法论：怎么拿一个新的车辆信号

1. **先确认服务端有这个 key** —— 从 `ZoneVehicleServer.apk` 的 dex 里 `strings | grep` 找
2. **不能靠猜** —— 加进 `keys.txt` 候选，用 `am broadcast -a ov.dash.scan` 运行时试读
3. 看 `files/scan.txt` 结果：`key|idx|service|value`，有值才算有效
4. 把命中的写回 `assets/keys.txt`（`KEY|service` 格式），部署到 `files/keys.txt`
5. 重启 app，日志会打 `extra keys loaded=N`

**不要手改 `files/keys.txt` 之后指望立刻生效** —— `loadExtra()` 只在 `onCreate` 跑，要 `am force-stop` 重启。

## 2026-11-25 实现服务端推送订阅，binder 读取开销降到 0

### 协议（从 IBmsService.aidl 反编译确认）

```java
// 各模块的 IXxxService 都有这四个 transact code
TRANSACTION_registerListener   = 1
TRANSACTION_unRegisterListener = 2
TRANSACTION_setXxxRequest      = 3   // 写
TRANSACTION_getXxxInfo         = 4   // 读（一直用的这个）
```

**读取协议的真相**：我们那 7 个参数就是 `BaseResult` 的 Parcel 结构

```java
writeString(key)
writeInt(1)                      // baseResult != null
writeInt(2000)                   // mCode（默认成功码）
writeString(null)                // mMessage
writeString("java.lang.Float")   // className
writeValue(0f)                   // mValue
writeValue(null)                 // mExtra
```

### 订阅实现

```java
// 订阅：把 Binder 和一个 flag 名字列表交给服务端
Parcel d = Parcel.obtain(), r = Parcel.obtain();
d.writeInterfaceToken(desc);
d.writeStrongBinder(myListener);
d.writeStringList(flags);
svc.transact(1, d, r, 0);
r.readException();
```

```java
// 回调：服务端 oneway 调我们的 onTransact(1)
data.enforceInterface("com.zone.api.vehicle.common.listener.IDataChangeListener");
String flag = data.readString();
if (data.readInt() != 0) {
    data.readInt();            // mCode
    data.readString();         // mMessage
    data.readString();         // className
    Object val = data.readValue(null);   // ← 实际值
    data.readValue(null);      // mExtra
}
```

### 三个实现要点

1. **监听器必须保引用** —— `List<Binder> listeners`，否则被 GC 掉回调就断了
2. **订阅后要 primeCache** —— 服务端只推「变化」，不推当前值，所以订阅完先同步读一遍填缓存（455/516 填上了，584ms）
3. **订阅成功后不再 fallback 到同步读** —— cache miss 的 key 直接跳过，否则每次失败调用约 6ms

### 实测效果

| 配置 | binder 次/秒 | 相对 baseline |
|---|---|---|
| 无 HUD | 1,150 | — |
| 173 轮询 | 1,671 | +521 |
| 516 轮询 | 1,878 | +728 |
| **516 订阅** | **1,489** | **+339** |

**读取开销从 170 次/秒降到 0，剩余 339 全部是 WebView 渲染。**

**516 个字段的订阅版，比 173 个字段的轮询版还省 11%。**

### 下一步（如果还要继续优化）

只剩 WebView 那 339 次/秒：
- 减少 `position:fixed` 元素数量
- 去掉 CSS 动画，只在 `onData` 里改 `textContent`
- 降低 `refresh` 到 2000ms

## 2026-11-25 实测：WebView 开销 100% 来自 CSS 动画

### 测量

```bash
adb shell "dumpsys gfxinfo ov.dash reset; sleep 6; dumpsys gfxinfo ov.dash | grep 'Total frames'"
```

| 页面 | 6 秒渲染帧数 | bobbin 次/秒 |
|---|---|---|
| 带 `@keyframes scan` + `pulse` | **359 帧（60fps 满帧）** | 1,489 |
| **去掉两个动画** | **0 帧（完全不重绘）** | **1,123** |

### 结论

**WebView 的 339 次/秒开销，全部来自持续 CSS 动画。**

去掉动画后 HUD 的额外开销**归零**——比无 HUD 的 baseline（1,150）还低一点（测量波动）。

关键点：**没有动画时，值不变就不重绘**。只有当页面确实改了 DOM 时才会重绘（信号每秒都在变，所以实际是每秒一次）。

### 完整性能账本

| 配置 | binder 次/秒 | 相对 baseline (1,150) |
|---|---|---|
| 173 轮询 + 动画 | 1,671 | +521 |
| 516 轮询 + 动画 | 1,878 | +728 |
| 516 订阅 + 动画 | 1,489 | +339 |
| **516 订阅 + 无动画** | **1,123** | **≈0** |

### 对「用户随便写 HTML」的判断

| 用户写法 | 额外开销 | 说明 |
|---|---|---|
| 静态 + 只改 `textContent` | **≈0** | 值不变就不重绘 |
| 带 CSS 动画 | **最多 +350 次/秒** | 60fps 满帧，不是无底洞 |
| 每帧重建整个 DOM | 更高，可能卡顿 | 这种写法本身也慢，用户自己会察觉 |

**最坏情况是有限的**：动画再多也就 60fps 封顶。
所以不需要在框架层做复杂的防护，**给个好模板 + 文档说明**就够。

### 可选的兜底措施（未实现）

- `refresh` 设下限（比如不低于 300ms），防止用户配成 50ms 把 CPU 拉满
- 启动时检测帧率，超过 50fps 就在日志里警告「页面有持续动画」

## 2026-11-25 媒体数据源：bind 车机媒体中心 + transact(21)

### 为什么标准 API 拿不到

```
dumpsys media_session:
  com.android.bluetooth   active=false  state=PAUSED  metadata=蓝色的故乡/童彤
  com.zone.service.mediacenter active=true state=null metadata=null
```

蓝牙的 MediaSession 没有 `setActive(true)`，所以 `getActiveSessions()` 和
`addOnActiveSessionsChangedListener` 都拿不到它。`dumpsys` 能看到是因为它列全部会话。
`getSessions()` 是 @hide，公开 SDK 没有。

### 车机私有 AIDL（clusterwall 用的同一套）

```java
PKG  = "com.zone.service.mediacenter"
CLS  = "com.zone.service.mediacenter.MediaCenterService"
DESC = "com.zone.api.mediacenter.IMediaService"

Intent i = new Intent(DESC);
i.setClassName(PKG, CLS);
bindService(i, conn, BIND_AUTO_CREATE);

// 拿到 IBinder 后：
parcel.writeInterfaceToken(DESC);
binder.transact(21, parcel, reply, 0);
int count   = reply.readInt();      // 0 = 无数据
String kind = reply.readString();   // "bt_music" / "radio" / ...
// 循环 readString 直到 dataSize，最多 200 个：
//   纯数字(>1000) → 时长/频率
//   30 位以上的 hex/UUID → 内部 mediaId，**必须过滤**
//   其余按顺序 → [0]歌名 [1]歌手 [2]专辑
```

**实测输出**：`mc -> 蓝色的故乡 / 童彤 / 草原传说 kind=bt_music n=3`

### 触发方式（无轮询）

| 触发源 | 切歌时会响 |
|---|---|
| `MediaSessionManager.onActiveSessionsChanged` | ✅（切歌时 session 状态变化） |
| `AudioManager.registerAudioPlaybackCallback` | 播放/暂停可能响 |
| `NotificationListenerService.onNotificationPosted` | 仅其他播放器 |

三个都挂上，任何一个响就调一次 `transact(21)`。

### 一个坑

返回的第一个字符串是 **UUID**（内部 mediaId），不是歌名。不过滤的话歌名位置就被它占了，
显示出来是一串十六进制。clusterwall 的 `isNoise()` 里有同样的规则。

## 2026-11-25 GPS 字段整个消失：前台服务缺 foregroundServiceType

### 现象

```
dumpsys location: Location[gps ... alt=83.0 ... satellites=19]   ← 系统有值
ACCESS_FINE_LOCATION: granted=true                               ← 权限也有
JSON 里：alt / lat / lon / sats 全都不存在                        ← 我们拿不到
```

不报错、不打日志、`getLastKnownLocation()` 就是返回 null。

### 原因

Android 10+ 规定：**前台服务访问位置必须声明 `foregroundServiceType`**，否则系统静默拒绝。

```xml
<!-- 错的 -->
<service android:name=".DashService" android:exported="true" />

<!-- 对的 -->
<service android:name=".DashService" android:exported="true"
         android:foregroundServiceType="location" />
```

权限、位置开关、GPS 定位全都正常，**唯一缺的就是这一行声明**。

### 教训

「权限 granted + 系统有数据」不等于「app 能拿到」。
服务类型的隐式限制不会报错，只会静默返回 null。
排查这类问题要逐层验证：权限 → 服务类型 → API 调用 → 返回值。

## 2026-11-25 双 WebView 方案失败：层级乱序

### 想做什么

主屏上同时要「桌面全屏卡片」和「顶部 66px 常驻条」，一开始拆成两个 config 屏、
两个 WebView、两个窗口。

### 为什么不行

1. **内存翻倍**——每个 WebView 是独立渲染进程（Chromium 实例）
2. **层级乱序**——两个 `TYPE_APPLICATION_OVERLAY` 同层级，Z 序由 `addView` 先后决定。
   `ui-debug` 配了 `onlyOnDesktop`，每次回桌面都重新 `addView`，于是排到了
   `ui-top` 之上，把顶部条整个盖住（它的背景是 `rgba(0,0,0,.82)`）
3. **两套 FileObserver、两套 JS 上下文**

### 正确做法：一个 WebView

```
一个 overlay 窗口（全屏透明）
└─ 一个 WebView
    └─ HTML 内部用 onDesktop 控制哪里画东西
```

```js
document.body.style.visibility = (d.onDesktop === false) ? 'hidden' : 'visible';
```

- 窗口常驻，**不销毁不重建**
- 进 app 时整页 `visibility:hidden`，窗口透明，app 内容完整透出
- 没有层级问题，内存只有一份

### 配套的坑

去掉 `onlyOnDesktop` 后 `topChecker` 不启动（原来 `needTopCheck()` 依赖它），
导致 `onDesktop` 恒为 `false`。要改成「有 `display: 0` 的屏就启动」。

### 判断标准

**一个 display 上只挂一个 overlay。** 需要分区域就靠 HTML 内部布局，
不要拆多个 WebView——WebView 的窗口层级不受我们控制，只受 `addView` 顺序影响。
